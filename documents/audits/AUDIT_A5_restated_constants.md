### F1 — HIGH — N16 undercut threshold (0.522) hardcoded in prompt prose, source of truth is a loaded JSON config

**Value / rule**: "reject an undercut recommendation unless P(undercut_success) >= 0.522".

**Every location**:
- `src/agents/pit_strategy_agent.py:230` — `self.undercut_threshold: float = uc_cfg['best_threshold']`, loaded from `data/models/pit_prediction/model_config_undercut_v1.json` (not in git; from HF Hub). **This is the actual source of truth.**
- `src/agents/pit_strategy_agent.py:1194,1200` — the real decision: `verdict = 'YES' if calib_proba >= agent.cfg.undercut_threshold else 'NO'`, and the tool's return string embeds `threshold={agent.cfg.undercut_threshold}`. Correctly reads the loaded config value.
- `src/agents/pit_strategy_agent.py:611` — **`_PIT_STRATEGY_SYSTEM_PROMPT`, a PLAIN (non-f-string) triple-quoted constant** (confirmed at line 599: `_PIT_STRATEGY_SYSTEM_PROMPT = """You are the Pit Strategy Agent...`, no `f` prefix): `"4. If P(undercut_success) >= 0.522 for any rival → recommend UNDERCUT."` — a literal that cannot track `uc_cfg['best_threshold']`.
- `notebooks/strategy/pit_prediction/N16_undercut.ipynb` (training/export cell) — writes `"best_threshold": 0.522` into the JSON. This is upstream of the config and not a runtime copy.

**Source of truth**: `data/models/pit_prediction/model_config_undercut_v1.json` → `self.undercut_threshold`. The prompt literal is a **dead copy**.

**Do they agree?** Computed: notebook export value is `0.522` (`notebooks/strategy/pit_prediction/N16_undercut.ipynb`, "Threshold (F1 val 2024, calibrated): 0.522"); prompt literal is `0.522`. **They currently agree** — by coincidence of when the prompt was last hand-edited, not by any mechanism. No test asserts equality (checked: no test reads `_PIT_STRATEGY_SYSTEM_PROMPT` at all — see `grep` for the constant name, 3 hits, none in `tests/`).

**Scale check (important negative result)**: unlike the historical #450/#665 bug, this one IS scale-consistent — the N16 notebook explicitly tunes `best_threshold` on the **calibrated** validation scores (`y_prob_val_cal`, cell "Step 3 · Platt calibration + final threshold"), and the runtime tool compares it against `calib_proba` (also post-calibration). So this is a **restatement risk**, not a live scale-mismatch bug like #450.

**What breaks if they drift**: N16 gets retrained (a routine event — the memory log already documents N14/N06/N10 retraining events changing baselines), the JSON `best_threshold` changes, `agent.cfg.undercut_threshold` picks it up automatically and the tool's actual YES/NO verdict changes — but the LLM is still told "0.522" in its own decision rule 4, so the prompt's stated policy and the tool's own reported `threshold=...` field in its return string would visibly disagree in the same conversation turn. Low probability of silent wrong-answer (the tool's return string *does* self-report the live threshold each call, so an attentive LLM sees the true value at inference time) but the system-prompt "rule" becomes stale documentation the model is trained to trust.

**Fix**: make `_PIT_STRATEGY_SYSTEM_PROMPT` an f-string like `race_situation_agent.py`'s already-fixed `_RACE_SITUATION_SYSTEM_PROMPT` (see "genuinely single-sourced" section below) — interpolate `{CFG.undercut_threshold:.3f}` at class-definition/instantiation time. Note `_PIT_STRATEGY_SYSTEM_PROMPT` is currently a **module-level** constant built before any `PitAgentCFG` instance exists (unlike N27, whose module-level `CFG` singleton is built above the prompt) — this needs either moving the prompt construction after `CFG = PitAgentCFG()`, or building it lazily per-agent-instance. Not a one-line change; scope it before promising it's small (lesson learned 2026-07-16, memory §11).

**Do they agree?** Computed by literal comparison: `0.30 == 0.30 == 0.30 == 0.30`. **They currently agree.** No test checks this — grepped `tests/` for `sc_reactive`, `sc_prob_threshold`, `0.30`/`0.3`: the only hits are unrelated numeric coincidences (`lap_time_pred` deltas) and two tests that pass `sc_reactive=False` as a literal constructor kwarg (not exercising the threshold logic at all).

**Semantic note (not a confirmed bug, flagged for measurement)**: this 0.30 cutoff is compared against the *same* variable (`RaceSituationOutput.sc_prob_3lap`, calibrated) that `race_situation_agent.RaceSituationConfig.high_sc = 0.0864` classifies as "HIGH" threat (documented: "fires on 1.27% of laps"), and N14's own training notebook records raw scores "concentrated in [0, 0.15] with only a few high-confidence predictions reaching 0.5+" pre-calibration. A calibrated 0.30 cutoff is therefore well above the "HIGH" threat band and plausibly fires only in genuine high-confidence SC scenarios — this reads as an intentionally *stricter* bar for the expensive N30 RAG call than for the cheap `threat_level` classification, not a scale-mismatch bug. Flagged MEDIUM rather than HIGH because I could not find a measured firing rate for `sc_prob_3lap > 0.30` over real 2025 laps (the kind of measurement `high_sc`/`high_overtake`'s docstrings cite) — recommend the same treatment #665 gave `high_sc`/`high_overtake`: measure the firing rate once, record it in the docstring, and add a `test_sc_bands_track_the_models_base_rate`-style regression test.

**What breaks if they drift**: `strategy_orchestrator` decides whether to spend a Qdrant/N30 call using ITS 0.30; `pit_strategy_agent` decides its own `sc_reactive` output flag (which callers — including the MC layer's `contingency echo` per the decision-memory doc — read to know whether "the pit call happened because of a Safety Car") using ITS OWN 0.30. If N14 is retrained and `strategy_orchestrator.CFG.sc_prob_threshold` is re-baselined (exactly the kind of change #665 already made once, to a sibling threshold), only `pit_strategy_agent.py`'s three copies (1 code literal + 2 prompt literals) are silently left behind — `sc_reactive` and "N30 activates" then disagree about the same lap's SC risk, and downstream memory/MC logic that treats `sc_reactive` as ground truth for "this was an SC-driven stop" gets it wrong at the OLD threshold forever.

**Fix**: import `strategy_orchestrator.OrchestratorCFG` (or extract `sc_prob_threshold` into a shared module both agents import — `guard_rails.py` is the precedent for "policy constant with no heavy imports") and use it at `pit_strategy_agent.py:1593`; f-string-interpolate the same value into the two prompt-prose lines.

### F3 — MEDIUM — Tyre cliff PIT_SOON/MONITOR bands (3 / 7 laps) hardcoded in tire-agent prompt prose; the runtime classifier is cluster-aware and CAN diverge per GP, the prompt structurally cannot

**Value / rule**: "P10 laps-to-cliff < 3 → PIT SOON, < 7 → MONITOR, else STAY OUT."

**Every location**:
- `src/agents/tire_agent.py:203-204` — `cliff_pit_soon_laps: int = 3`, `cliff_monitor_laps: int = 7` (dataclass field defaults on `TireAgentCFG`).

- `src/agents/tire_agent.py:720,732-734` — `_TIRE_SYSTEM_PROMPT`, a **plain (non-f-string) triple-quoted constant** (confirmed no `f` prefix at line 720): `"STAY OUT — P10 > 7 laps remaining"`, `"MONITOR — P10 between 3 and 7 laps"`, `"PIT SOON — P10 < 3 laps"`. Hardcoded, GP-independent, cannot reference `CFG.get_cliff_thresholds(gp_name)` because it is a module-level string built once at import, not per-call.

**Source of truth**: `TireAgentCFG.get_cliff_thresholds(gp_name)`, backed by `tire_agent_config_v1.json`.

**Do they agree?** Computed: global JSON `(3, 7)` == dataclass defaults `(3, 7)` == prompt prose `(3, 7)` (verified by reading the deserialized JSON directly: `{"cliff_pit_soon_laps": 3, "cliff_monitor_laps": 7, ...}`, no `cluster_aware_thresholds` key present). **They currently agree**, because `cluster_aware_thresholds` is unpopulated. The moment that block is populated for even one cluster or GP (the code path exists specifically to let "Mexico City at altitude"-style outliers be tuned individually, per the `tire_agent.py:284-287` docstring — this is an anticipated, not hypothetical, future edit), the prompt's `_TIRE_SYSTEM_PROMPT` silently goes stale for every circuit whose override differs from 3/7, while `TireOutput.warning_level` (the actual categorical signal N28/N31 consume) uses the correct per-circuit value. The LLM agent would then be reasoning from `predict_tire_deg_tool`/`estimate_laps_to_cliff_tool` raw numbers against a stated 3/7 boundary while the STRUCTURED `warning_level` field it also has access to (built into the tool's own return string, per `tire_agent.py:1158`) reflects a different boundary for that GP.

**What breaks if they drift**: the LLM's own stated reasoning ("P10 between 3 and 7 laps → MONITOR") would contradict the `warning_level` field already computed and handed to it in the same tool call, for any circuit with a tuned override. Silent, not crash-shaped — a coherence bug in the agent's stated rationale, not a wrong number reaching N31 (N31 reads `warning_level`, the correct field, not the prose).

**Fix**: same shape as F1/F2 — make `_TIRE_SYSTEM_PROMPT` per-instance (built in `TireAgent.__init__` or lazily) and f-string interpolate `self.cfg.get_cliff_thresholds(gp_name)`; since the prompt is currently built before `gp_name` is known (module load time), this needs the same "build per-call, not at import" restructuring flagged for F1. Lower urgency than F1/F2 because the divergence has not yet been triggered by data (`cluster_aware_thresholds` is empty) — but it will trigger silently, with no test to catch it, the day someone runs "N26 Step 6" (referenced by `tire_agent.py:262`'s own docstring) and commits populated per-cluster thresholds.

### F4 — HIGH — Compound-vs-remaining-laps boundaries in the pit prompt's own "HARD constraints" section DISAGREE, TODAY, with the tool it tells the LLM to call

**Value / rule**: "which compound is legal/sensible to fit, given laps remaining."

**Every location**:
- `src/agents/pit_strategy_agent.py:91` — `_STINT_CAPACITY_LAPS: dict[str, int] = {'SOFT': 18, 'MEDIUM': 30, 'HARD': 38}`. Used directly by `recommend_compound_tool` (line 1255: `candidates = sorted(valid, key=lambda c: _STINT_CAPACITY_LAPS[c])`; line 1268-1271: `recommendation = next((c for c in candidates if _STINT_CAPACITY_LAPS[c] >= laps_remaining), candidates[-1])`). **This is the actual runtime source of truth for what the tool recommends.**
- `src/agents/pit_strategy_agent.py:1213-1215` (tool docstring) — `"Priority 2 — Pirelli average stint capacities (SOFT ~18 laps, MEDIUM ~30 laps, HARD ~38 laps) as fallback."` — matches `_STINT_CAPACITY_LAPS` exactly, correctly derived from the same source.
- `src/agents/pit_strategy_agent.py:654-658` — `_PIT_STRATEGY_SYSTEM_PROMPT` (plain, non-f-string), in the section literally headed `"## Strategic guard-rails (HARD constraints — override any decision rule above)"`: `"SOFT: recommend only if remaining laps <= 15... MEDIUM: suitable for 12-30 remaining laps... HARD: suitable for 20+ remaining laps."` — **different numbers: 15 / 12-30 / 20+, not 18 / 18-30 / 30+.**

**Source of truth**: `_STINT_CAPACITY_LAPS`, read by `recommend_compound_tool` — the tool decision rule 3 (`"Call recommend_compound_tool to determine the optimal compound"`) tells the LLM to call. The "HARD constraints" prose is a second, independent restatement with DIFFERENT numbers.

**Do they agree? Computed, not eyeballed**: derive the tool's actual decision boundary from `_STINT_CAPACITY_LAPS` and the `next(... >= laps_remaining ..., candidates[-1])` selection (candidates sorted ascending SOFT→MEDIUM→HARD when the current compound doesn't force exclusion): the tool selects SOFT for `laps_remaining <= 18`, MEDIUM for `18 < laps_remaining <= 30`, HARD for `laps_remaining > 30`. The prompt states SOFT only for `<= 15`, MEDIUM `12-30`, HARD `20+`.

Concrete counter-example at `laps_remaining = 16`: `_STINT_CAPACITY_LAPS['SOFT'] = 18 >= 16` is True, and SOFT sorts first among candidates, so **`recommend_compound_tool` returns `Recommended: SOFT`**. The prompt's own "HARD constraint" reads: *"SOFT: recommend only if remaining laps <= 15"* — `16 > 15`, so by the prompt's stated rule **SOFT must NOT be recommended here.** The tool the prompt tells the LLM to trust, and the "HARD constraint" the same prompt tells the LLM overrides "any decision rule above," **contradict each other on this input, today, with no retraining or config change required.**

**What breaks**: this is not a future-drift risk like F1-F3 — it is a **live, reachable disagreement inside a single prompt**, on any lap with 16, 17, or 18 laps remaining where the model is choosing a compound near a stint boundary (16-18, 30-31 give the same shape of conflict at the MEDIUM/HARD edge: tool switches to HARD only above 30, prompt says HARD "suitable" from 20). Best case the LLM notices the tool's own returned recommendation and ignores the inconsistent prose. Worst case: an LLM instructed that guard-rails "override any decision rule above" follows the prose literally, refuses the tool's SOFT recommendation at 16-18 laps remaining, and picks a harder compound than the deterministic model would — silently changing the agent's compound choice near common late-stint pit windows, with no error, no log line, and no test that would catch it (grepped `tests/` for `_STINT_CAPACITY_LAPS`, `18`, `remaining laps <= 15` in an assertion context: no hits tying the prompt text to the tool's boundary).

**Fix**: the "COMPOUND vs REMAINING LAPS" guard-rail block should either (a) be deleted — `recommend_compound_tool` is already the authoritative source and workflow rule 3 already tells the LLM to call it, so this prose is redundant with a worse copy of the same rule, or (b) if kept as a sanity-check bound for the LLM's own reasoning independent of the tool, be f-string-interpolated from `_STINT_CAPACITY_LAPS` the same way F1-F3 recommend, so the two can never state different numbers again.

### F6 — HIGH — The MC decision window (5 laps) is a bare literal restated in THREE modules across THREE different subsystems, admitted in a comment to require manual sync, and the ONE test that checks it re-derives the same literal instead of importing any of them

**Value / rule**: "the Monte Carlo / decision-evaluation horizon is 5 laps."

2. `src/strategy/eval/decision_modes.py:76` — `DECISION_WINDOW_LAPS = 5`, with an explicit comment 2 lines above admitting the coupling: `"Laps either side of the real stop that the stack is asked about. Five matches the Monte Carlo decision window, so the question posed to the model is the one it was built to answer rather than a horizon it never considers."` **The comment states the two constants must match. Nothing enforces it** — `decision_modes.py` does not import `WINDOW_LAPS` from `strategy_orchestrator` (confirmed: `decision_modes.py`'s only cross-module import is `from src.strategy.inference.guard_rails import ...`, not `strategy_orchestrator`).
3. `scripts/measure_mc_tables.py:83` — `WINDOW_LAPS = 5`, no docstring tying it to the other two. This is the constant that generates the COMMITTED `data/mc_measured_v1.json` (confirmed by reading the live file: top-level `"window_laps": 5`, and `sc_window.definition`: `"the number of RACING laps ... among the next W laps"`, `sc_window.window_laps: 5`). This is the highest-consequence copy: if it ever diverges from `strategy_orchestrator.WINDOW_LAPS`, the MC engine would score strategies over an N-lap horizon using probability tables (`sc_window`, `stop_hazard`, `gap_density`) that were empirically measured over a DIFFERENT-length horizon — the exact "threshold tuned on one scale, applied on another" shape as the historical #450/#665 bug, just for a window length instead of a probability cutoff.

**Source of truth**: none, structurally. Three independent module-level integer literals, one comment admitting the coupling, zero imports enforcing it.

**Do they agree? Computed**: `strategy_orchestrator.WINDOW_LAPS = 5`, `decision_modes.DECISION_WINDOW_LAPS = 5`, `measure_mc_tables.WINDOW_LAPS = 5`, live `data/mc_measured_v1.json["window_laps"] = 5` (read directly from the committed file). **All four currently agree.** No test asserts the cross-module relationship; `test_mc_measured_tables.py` only re-derives the same number the JSON already contains.

**What breaks if they drift**: `strategy_orchestrator.WINDOW_LAPS` is the kind of constant that gets revisited — its own comment block (`strategy_orchestrator.py:619-628`) already documents a deliberate departure from the published literature ("Heilmeier minimises total race time; van Kampen et al. 2024 argues against short horizons... A short window is a deliberate simplification") and flags it as a candidate for future widening. If it is widened to, say, 8 laps without also re-running `scripts/measure_mc_tables.py` and regenerating `data/mc_measured_v1.json`, the engine would evaluate an 8-lap strategy horizon while `sc_window`/`stop_hazard`/`gap_density` still describe 5-lap-window statistics — silently wrong MC scores, no exception, and `test_mc_measured_tables.py:63` would still pass (it only checks the JSON says what it says, not that anything downstream still agrees with it). `decision_modes.DECISION_WINDOW_LAPS` drifting separately would mean the eval tier grades agreement between the no-LLM stack and real stops over a *different* horizon than the one the model was actually built to answer — reintroducing exactly the mismatch its own comment says the number exists to prevent.

**Fix**: pick one source of truth — `strategy_orchestrator.WINDOW_LAPS` is the natural owner since it is the live decision boundary. Have `decision_modes.py` import it directly (`from src.agents.strategy_orchestrator import WINDOW_LAPS as DECISION_WINDOW_LAPS`, accepting the heavier import since `decision_modes.py` already pulls in `guard_rails` and is part of the eval tier, not the model-free CI path — verify against its own "never from `no_llm`" comment before doing this, since that comment specifically objects to importing anything that loads model weights at import time; `strategy_orchestrator.py` does load agent modules, so this may require hoisting `WINDOW_LAPS` into a leaf module, mirroring exactly how `guard_rails.py` was extracted from `no_llm.py` for the identical reason in #708). `scripts/measure_mc_tables.py` should import the same constant rather than restating it, and `test_mc_measured_tables.py:63` should assert `tables["window_laps"] == strategy_orchestrator.WINDOW_LAPS` (or whatever the single post-fix source is) instead of the bare `5`.

## Summary

Six real findings (F1-F6), one low-priority note (F7). **All six real findings live in the same place: a numeric threshold, boundary, or rule stated once in code (or JSON) and restated at least once more — most often in LLM system-prompt prose, which by construction cannot import anything.** Two (F4, F5) are provable, present-day disagreements, not latent risk — the compound-selection boundary the pit agent's own tool computes (18/30/38 laps) already contradicts what BOTH the pit agent's prompt and the orchestrator's prompt tell the LLM (15/12-30/20+), reachable on any real lap with 16-18 laps remaining. The other four (F1, F2, F3, F6) are currently-agreeing pairs/triples with no import and no test holding them together, each one lap of a retraining or a config change away from silently disagreeing — exactly the shape of every historical bug this audit was briefed to hunt for. The single highest-leverage structural fix available is the one `race_situation_agent.py` already demonstrates: make agent system prompts f-strings that read live config objects, not plain triple-quoted text with typed-in numbers.
